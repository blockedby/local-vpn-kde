# Релизы через PR

Номер версии хранится в корневом [`VERSION`](../VERSION), например `0.2.0`.
Git-тег добавляет префикс `v`: `v0.2.0`. CI не увеличивает номер автоматически.

1. В PR в `main` измените `VERSION` и проверьте изменения.
2. Когда версия одобрена к выпуску, поставьте метку **`release`** до слияния.
3. Слейте PR. Это разрешает сборку и публикацию именно слитой ревизии.
4. Результат появится в GitHub Releases после успешных проверок и загрузки.

Без метки `release` слияние ничего не публикует. Простое добавление метки,
закрытие PR без merge, push или создание тега также ничего не запускают.
Добавление метки уже после merge не выпускает версию задним числом.
Релизный PR должен менять `VERSION`; номер должен быть выше всех существующих
стабильных тегов. Примеры: `0.2.1` — исправления, `0.3.0` — новые возможности,
`1.0.0` — согласованная первая полноценная стабильная версия.

## Что делает CI

- Проверяет событие merge, метку, `VERSION` и точный SHA результата слияния.
- Запускает Go race-тесты, проверку типов и тесты TUI, тесты процесса выпуска.
- Собирает `.pkg.tar.zst` для Arch x86_64 и `.deb` для Debian 13 amd64,
  проверяет установку пакетов в изолированных контейнерах.
- Собирает отдельный Docker-архив установщика из того же SHA.
- Сверяет контрольные суммы и ревизии всех артефактов.
- Только после этого создаёт аннотированный тег, загружает файлы в draft-релиз,
  скачивает их и проверяет байты по исходным SHA-256. Затем публикует релиз.

Неуспешная проверка до публикации не создаёт тег. Если загрузка или проверка
GitHub завершилась ошибкой уже после создания тега, тег и возможный draft
сохраняются для разбора. Ничего не перезаписывается и автоматически не повторяется.
Исправление исходников получает новый номер; восстановление прерванной публикации
той же ревизии требует отдельного решения.

Workflow работает на событии `pull_request`, а не `pull_request_target`.
Используйте релизный PR из ветки этого репозитория: для PR из fork GitHub может
ограничить токен правами чтения и не разрешить публикацию. Если merge выполняется
автоматизацией через `GITHUB_TOKEN`, GitHub также может подавить следующий запуск;
для обычного выпуска сливайте PR в интерфейсе GitHub или от имени сопровождающего.

## Состав релиза

Native-пакеты включают скомпилированный TUI, Go-службы, sing-box и интеграцию с
системой. NetworkManager, OpenVPN, systemd, polkit и сетевые утилиты остаются
системными зависимостями. Установка через пакетный менеджер не подключает VPN;
первичная настройка в TUI запрашивает авторизацию пользователя.

Docker-архив — отдельный вариант: `./install.sh`, затем `./run.sh` без sudo.
Это установщик со сборкой и зависимостями, а не один самостоятельный VPN-бинарник.
Релиз также содержит архивы исходников native-пакетов, метаданные сборок и общий
`SHA256SUMS`.

Ручной workflow **Manual native package candidates** остаётся для пробных
сборок без публикации. Его запуск — отдельное действие. См. [пакеты](native-packages.md).

## Перед первой публикацией

Метка `release` означает готовность к выпуску, а не просьбу просто попробовать CI.
До её установки должны быть завершены необходимые проверки платформ и вопросы
лицензирования. На этапе подготовки v0.2.0 проверка Debian в полноценной VM с
KDE/NetworkManager и условия публичного распространения ещё требуют завершения.
Контейнерные проверки не заменяют эту приёмку.

Технические справки: [события GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request),
[аннотированные Git-теги](https://docs.github.com/en/rest/git/tags#create-a-tag-object).
